# 402 鼠王争霸赛 · 原生微信小程序

这不是 `web-view` 网页壳。`pages/` 是微信原生页面（WXML/WXSS/JS），`lib/api.js` 连接网页 V1 同一个 Supabase 项目，`lib/standings.js` 计算排行榜。使用正式 AppID `wxe5fcf6be56ed781e` 导入本目录即可在开发者工具中编译。没有使用或开通微信云开发。

## 当前已实现

- 首页从原项目的 `profiles`、`meals` 读取真实数据，展示主厨榜、菜品榜和最近一餐；沿用鼠王与厨师头像素材。
- 原生发布页：选照片、自动识别、改菜名、添加或删除漏识别菜品、重新识别、选择日期/午晚餐/厨师、上传到现有 Storage 并保存到现有 `meals`。
- 原生评委页：选餐次，按 0.5 分调整，由 Supabase Edge Function `mini-meal-update` 更新餐次和菜品分数。该函数要求已验证的 Supabase 用户 JWT，不使用 service role。
- 删除餐次时调用 `mini-meal-delete`：在服务端检查是否有其他餐次共用同一张图片，只清理本项目 `meal-photos` 中未被复用的图片；清理失败时保留餐次，避免产生“记录已删但图片清理失败”的半完成状态。
- 首页可主动选择微信头像并填写昵称；首次打开不会自动向微信申请登录凭证，也不读取微信号。用户主动保存资料时才建立小程序身份关联；资料和身份映射仅由 `wechat-session` Edge Function 写入，数据库只保存 OpenID 哈希，不保存原始 OpenID 或 UnionID。
- 只在客户端使用可公开的 Supabase publishable key。SiliconFlow 密钥和微信 AppSecret 都只留在 Supabase Edge Function Secrets。
- 微信登录 Edge Function `wechat-session` 已部署，OpenID 会先做哈希再用于账号映射；真实微信登录码尚未在手机上走通验收。

## 当前发布状态与上线门槛

1. **后端与域名**：Supabase 项目状态为 `ACTIVE_HEALTHY`；`recognize-dishes`、`mini-meal-update`、`mini-meal-delete`、`wechat-session` 四个 Edge Function 均处于 `ACTIVE`，删除函数启用 JWT 校验。用户确认已在微信后台保存 Supabase 的 request、downloadFile 域名；开发者工具中 `profiles`、`meals` 与 Auth 请求曾返回 HTTP 200。真机上的网络白名单、照片上传和图片回显仍待验证。
2. **真机端到端验收**：最新 1.0.5 已包含首页、发布、评委、管理餐次、管理厨师页面、隐私授权提示和餐次图片清理。仍需在手机上验证微信身份关联、照片识别与耗时、Storage 上传和回显、发布保存、评分保存，以及管理编辑/删除。自动化与模拟器检查没有新增或修改线上餐次、评分数据；真机验收也应先避免用生产数据做破坏性测试。
3. **微信身份**：`wx.login` → Supabase Edge Function → 微信 OpenID 的后端链路已部署，但真实微信登录码尚未在真机走通。微信号不能由小程序直接读取；头像和昵称仅在用户主动选择后保存。登录失败时会回退到匿名 Supabase 会话。
4. **微信隐私合规**：原生小程序已启用隐私检查，并注册 `wx.onNeedPrivacyAuthorization`；统一授权组件提供查看平台隐私指引、同意和拒绝路径。公众平台的《用户隐私保护指引》仍未核验配置，需如实说明 OpenID 哈希身份关联、用户主动选择的头像/昵称、餐桌照片经 SiliconFlow 识别并存入 Supabase，以及拿到小程序的用户共同查看/编辑/删除共享记录；还要在真机验证同意、拒绝两条路径。代码接入不等于平台合规验收完成。

   **供填写平台指引的内容草稿（上线前仍须核对）：**

   - **收集的信息与用途**：用户主动保存资料时，小程序调用微信登录能力取得一次性登录凭证，服务端向微信换取小程序身份标识并生成哈希，用于识别同一小程序账号；不读取微信号、手机号，也不保存原始 OpenID。用户可主动选择头像并填写昵称，用于资料展示。用户选择发布餐桌照片时，照片会发送给菜品识别服务用于识别菜名；用户确认发布后，照片、菜名、餐次日期与午晚餐类型、厨师关联和评分会写入 Supabase，用于展示排行榜和管理餐次。执行发布、评分或管理操作时，系统还会使用 Supabase 登录会话及其内部账号标识完成保存和权限校验。
   - **接收/处理信息的服务**：微信提供小程序登录凭证及用户主动选择头像的能力；Supabase 提供登录会话、数据库和文件存储；SiliconFlow 接收用户主动提交识别的餐桌照片并返回识别结果。请在平台表单中按其实际字段，分别补充服务商名称及处理目的。
   - **共享范围**：当前产品采用共享数据模式。任何能使用该小程序的用户都可以查看、编辑或删除全部餐次和厨师记录并提交评分；餐桌照片和头像使用公开访问地址展示，知道图片地址的人也可能直接访问。不要把链接描述成访问权限控制。
   - **保存与删除**：餐次和厨师记录保存在 Supabase 数据库，照片/头像保存在 Supabase Storage。小程序 1.0.5 删除餐次时会尝试清理未被复用的餐桌照片；此前遗留的孤立照片、厨师自定义头像，以及从网页端删除记录产生的文件目前没有统一清理流程。微信账号身份映射也没有小程序内自助删除入口。因此，保留期限和全部数据删除流程尚未闭环，不能承诺“删除记录后所有数据立即清除”或指定未经确认的保留期限。

   这段是依据现有代码整理的产品说明，不是法律意见，也不是已发布的平台隐私政策；提交前由小程序账号管理员核对平台表单字段、服务商隐私政策链接及实际存储/删除规则。
5. **备案**：小程序备案状态尚未确认完成。工信部要求境内从事互联网信息服务的 APP（包括小程序）履行备案手续，未备案不得提供该项互联网信息服务。工信部登记表支持个人主办者，个人填写姓名和有效证件；小程序免填域名、公钥/MD5及网络接入信息，但仍需填应用名称/图标、运行平台、SDK 服务商/类型、类目及语种。公众平台可能另有校验要求，最终以账号后台为准。[工信部备案表](https://xzca.miit.gov.cn/bsfw/bszn/art/2024/art_5d3cc7f452c04fdd97b6881a20b656f9.html)
6. **体验、审核、发布**：先在公众平台「管理 → 版本管理」将 1.0.5 开发版本设为体验版，生成体验版二维码并完成真机验收；验收通过且备案、隐私指引等平台配置齐备后，再由账号管理员提交审核。只有审核通过并执行发布，才算正式上线。本次明确没有提审或正式发布。
7. **访问权限按用户确认的共享模式执行**：用户已确认收到小程序链接的用户都应有权限。线上 RLS 允许任何匿名/已登录会话读取全部厨师和餐次，并更新或删除所有厨师与餐次；照片公开可读。分享链接不是身份验证，因此实际应按“拿到小程序即可操作共享数据”理解。Supabase 安全顾问报告匿名访问策略提示，符合当前共享模式但仍需接受其风险。
